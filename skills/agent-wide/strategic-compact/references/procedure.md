# Strategic context compaction

## Use

Compact when context pressure is high and a phase has ended: research has become
an approved plan, an integrated increment has closed, or the next action belongs
to a materially different problem.

Do not compact while a command, edit, conflict resolution, diagnosis, review, or
unrecorded decision is in flight.

Validate the complete continuation record and its durable owner before invoking
the harness's single selected compaction action. Missing, conflicting, or
transient-only context stops without compacting; never substitute an invented
persistence surface or reduced recovery packet.

## Boundary test

Before suggesting the active harness's compaction action, prove all of these:

1. The current phase has a decisive outcome, not merely elapsed time or many tool
   calls.
2. Intent, constraints, touched paths, owners, evidence, blockers, and the exact
   next action are stored in the repository's authorized durable surface.
3. No secret, partial edit, transient terminal output, or unrecorded operator
   correction is the only copy of required context.
4. The next phase can re-read its authority and repository state without guessing.

## Continuation record

Preserve only verified facts:

- objective and exclusions;
- current branch and integration target;
- changed and attributed WIP;
- commands, exits, and decisive output;
- active blockers and unresolved decisions;
- next owner action and invalidated evidence that must be rerun.

After compaction, reload project law, the durable record, and live repository
state. Treat summaries as navigation, never as a substitute for current files or
runtime evidence.

Persist the complete record before compaction as one atomic boundary. If that
write fails, propagate the cause and leave the active context intact.
