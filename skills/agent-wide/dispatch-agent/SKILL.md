# dispatch-agent

Activate only when a bounded task materially benefits from one specialist
exposed by the active client's current roster. A direct bounded answer does not
activate delegation.

Before the native dispatch effect, resolve the exact objective, complete current
roster, trigger evidence, selected capability, authorized scope, relevant
project context, native API, and required return evidence. A missing or
conflicting roster, interface, authority, or boundary stops with zero effects.

Select exactly one agent by strongest material trigger overlap and state the
confidence evidence. Model, tier, family, variant, and provider remain owned by
the active runtime; never use a bundled/cached roster, general fallback, alias,
second agent, substitute lane, workspace, or tracker path.

Publish one complete handoff through the current native API only after preflight.
The first dispatch, timeout, signal, or child failure propagates unchanged and
produces no partial handoff or success claim. Cleanup may attach a secondary
failure only while re-raising the first cause and removing dispatch residue.

Report the selected agent, confidence, preserved scope/context, native handoff
evidence, and expected result. Delegated mutation remains governed by the active
project's existing owners.
